# confetti 캔버스 재활용 수정 전/후 메모리 측정 (2026-10-09)

대상 수정: `962b412` — 결과 화면마다 새 캔버스 + `confetti.create(..., { useWorker: true })` 를 만들던 것을, 앱 전체에서 캔버스·인스턴스 하나를 재활용하도록 변경.

- 수정 전: `d3630fc`
- 수정 후: `962b412`

## 측정 방법

- 각 커밋을 `electron-vite build` 한 실제 앱을 그대로 띄우고, 마우스 입력(`webContents.sendInputEvent`)으로
  **메인 → 설문 5문항 → 로딩(2.2초) → 결과(5초 표시, confetti 발사) → 처음으로** 를 1회로 60회 반복.
- 매 회 메인으로 돌아온 뒤 2초 기다렸다가 `app.getAppMetrics()` 의 프로세스별 `privateBytes` 합계를 기록
  (앱의 `src/main/metrics.ts` 와 같은 기준). 결과 화면 표시 중 값도 따로 기록.
- 강제 GC 없음 (현장 상태 그대로). 소리 음소거. userData 는 별도 폴더로 분리.
- 수정 후 버전의 "50회마다 자동 새로고침"은 메인 5초 무입력이 조건인데 측정은 2초 뒤 다음 회를 시작하므로
  **발동하지 않음** → 순수하게 캔버스 재활용 효과만 비교.
- 환경: Windows 11, Electron 33.4.11, Intel Iris Xe + Arc A350M.
- 조건 2가지: ① 창 모드 704x1241, ② 세로 모니터 전체화면 1080x1920 (현장 키오스크와 비슷한 조건).

## 해석

1. **이 PC에서는 "반복할 때마다 일정량씩 계속 증가"하는 누수가 재현되지 않았다.**
   두 버전 모두 첫 1회에서 약 +190~310MB 뛰고(GPU 래스터·이미지 디코드 캐시 등 1회성), 이후 60회까지 평탄하다.
2. 그래서 `(60회 후 − 시작) ÷ 60` 으로 "회당 증가량"을 내면(전체화면 수정 전 8.3MB/회) **틀린 표현**이 된다 —
   증가분 거의 전부가 1회차에서 한 번 생긴 것이고, 2~60회 기울기는 0에 가깝다.
3. 수정 효과로 확인된 것은 **결과 화면(confetti 발사 중) 최대 메모리 1,067MB → 811MB (−24%)**,
   GPU 프로세스 안정 구간 550MB → 500MB. 화면 해상도가 클수록 차이가 커진다(창 모드에서는 차이 없음).
4. 코드 주석에 적힌 "수십 건 뒤 GPU 메모리가 GB 단위" 증상은 현장 하드웨어/드라이버 조건에서 생긴 것으로 보이며,
   이 PC 측정으로는 회당 37MB 를 뒷받침할 수 없다. 그 수치를 쓰려면 현장 기기 로그(수정 후 버전부터 `metrics` 줄이
   5분마다 남음)나 당시 기록이 필요하다.

## 원자료

- `fullscreen/before.jsonl`, `fullscreen/after.jsonl` — 1080x1920 전체화면, 0~60회
- `windowed/before.jsonl`, `windowed/after.jsonl` — 704x1241 창 모드, 0~60회
- `bench.js` — 측정 스크립트, `analyze.js` — 집계 스크립트 (`node analyze.js fullscreen`)

각 줄: `iter`(회차), `total`(전체 MB), `procs`(프로세스별 MB), `resultTotal`(결과 화면 표시 중 MB), `fps`, `cycleMs`, `heap`(JS 힙 MB).

재실행: 커밋별 worktree 를 만들어 `electron-vite build` 후
`BENCH_DIR=<worktree> BENCH_ITERS=60 BENCH_OUT=<경로>.jsonl BENCH_LABEL=<이름> [BENCH_FULLSCREEN=1] electron bench.js`
(VS Code 터미널에서는 `ELECTRON_RUN_AS_NODE` 를 먼저 해제).
